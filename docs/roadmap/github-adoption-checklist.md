# NeuronAgent GitHub Adoption Checklist

> Last updated: 2026-04-30  
> Purpose: Track open-source health metrics and adoption assets  
> Target: Complete before any public announcement or GitHub promotion

A developer who finds NeuronAgent on GitHub should be able to answer five questions in under five minutes:
1. What is it?
2. Can I install it?
3. Does it work?
4. Can I trust it?
5. How do I contribute?

This checklist tracks everything needed to answer all five questions.

---

## Repository Health

### Profile and metadata

- [ ] Repository description is set (one sentence, accurate)
- [ ] Repository topics are set: `ai-agent`, `postgresql`, `rag`, `llm`, `neurondb`, `golang`, `agent-runtime`
- [ ] Repository website is set (docs site or neurondb.ai/neuronagent)
- [ ] Repository is public
- [ ] Default branch is `main`
- [ ] Branch protection on `main`:
  - [ ] Requires PR review before merging
  - [ ] Requires status checks to pass
  - [ ] No direct pushes to `main`

### License

- [ ] `LICENSE` file exists at repository root
- [ ] License is clearly stated in README
- [ ] License is appropriate for intended use (confirm: Apache 2.0 or MIT for open source, or other for commercial)

---

## README Quality

A new visitor should understand the project within 90 seconds of reading the README.

- [ ] First two sentences explain what NeuronAgent is, for whom, and why it matters
- [ ] Install instructions appear before architecture explanations
- [ ] Install requires 4 or fewer commands
- [ ] A demo is visible (GIF, terminal recording, or screenshot) near the top
- [ ] "What you get" section lists concrete capabilities (not architecture fog)
- [ ] "Why NeuronAgent" section positions it against alternatives in plain language
- [ ] Use cases section has 4–6 real scenarios with links to examples
- [ ] Links to docs, contributing guide, and security policy
- [ ] Badges are real (only for workflows that exist and pass)
- [ ] Go version badge matches `src/go.mod`
- [ ] No dead links
- [ ] No commands that don't work on a clean machine
- [ ] No feature claims without backing code

---

## Demo and Visuals

- [ ] Demo GIF exists in `docs/assets/demo.gif`
- [ ] Demo GIF is linked from README
- [ ] Demo GIF shows: install → start → create agent → run demo → see output
- [ ] Demo GIF is generated by a script (`scripts/record-demo.sh`), not created manually
- [ ] Demo GIF is under 5 MB (use palette optimization)
- [ ] Terminal recording uses clean, readable font and colors
- [ ] At least one screenshot of agent output

---

## Install and Quickstart

- [ ] README install works on Linux (tested)
- [ ] README install works on macOS (tested)
- [ ] README install works on Windows with Docker Desktop (tested or explicitly documented as unsupported)
- [ ] `scripts/install.sh` is hosted at the stated URL
- [ ] `curl | bash` install works on a clean machine
- [ ] Clone → compose → demo path works in under 5 minutes
- [ ] `.env.example` is present and accurate
- [ ] Install instructions handle the most common error: Docker not running

---

## Examples and Demos

- [ ] `examples/` directory has at least 3 working examples
- [ ] Each example has a `README.md`
- [ ] Each example has a working demo script
- [ ] Examples are linked from the README
- [ ] Examples are linked from the docs
- [ ] Examples cover different use cases (not all the same feature)
- [ ] Examples use the public API (no direct DB access, no internal packages)
- [ ] Examples have a cleanup command

---

## Documentation

- [ ] `docs/` directory is organized (not a flat list of mixed .md and .txt files)
- [ ] `docs/quickstart.md` is the entry point for new users
- [ ] `docs/index.md` exists as a navigation page
- [ ] All doc pages are reachable from either README or `docs/index.md`
- [ ] No `.txt` files in `docs/` (all converted to `.md`)
- [ ] No empty doc pages
- [ ] No doc pages claiming features that don't work
- [ ] All links in docs resolve
- [ ] Docs cover: install, quickstart, concepts, API, memory, RAG, tools, workflows, security, observability, deployment
- [ ] At least one architecture diagram with clear labels

## Community Files

### Required for open-source health score

- [ ] `CONTRIBUTING.md` exists at repository root
  - [ ] Development environment setup
  - [ ] How to run tests
  - [ ] How to submit a PR
  - [ ] Code style requirements
  - [ ] How to file an issue
- [ ] `CODE_OF_CONDUCT.md` exists at repository root
  - [ ] Based on Contributor Covenant (or equivalent)
  - [ ] Enforcement contact is specified
- [ ] `SECURITY.md` exists at repository root
  - [ ] How to report a vulnerability (email or private advisory)
  - [ ] Response time commitment
  - [ ] Supported versions
- [ ] `SUPPORT.md` exists or is covered in CONTRIBUTING
  - [ ] Where to get help (GitHub Discussions, Discord, etc.)
  - [ ] What belongs in Issues vs Discussions

### Recommended

- [ ] `CHANGELOG.md` has at least one versioned release entry
- [ ] `ROADMAP.md` links to `docs/roadmap/6-month-world-class-plan.md`

## Issue Templates

- [ ] `.github/ISSUE_TEMPLATE/bug_report.yml` exists
  - [ ] Template captures: description, steps to reproduce, expected vs actual, version, OS, Docker version
- [ ] `.github/ISSUE_TEMPLATE/feature_request.yml` exists
  - [ ] Template captures: problem statement, proposed solution, alternatives considered
- [ ] `.github/ISSUE_TEMPLATE/documentation.yml` exists
  - [ ] Template captures: what doc is wrong/missing, what should be there
- [ ] `.github/PULL_REQUEST_TEMPLATE.md` exists
  - [ ] Includes: summary, testing done, breaking changes, docs updated

## Labels

- [ ] Standard label set is configured:
  - `bug` — red
  - `enhancement` — blue
  - `documentation` — green
  - `good first issue` — light green
  - `help wanted` — yellow
  - `question` — purple
  - `wontfix` — white
  - `needs triage` — orange
  - `blocked` — dark red
  - `breaking change` — dark orange
  - `P0`, `P1`, `P2`, `P3` — priority levels
  - `Track-A` through `Track-J` — engineering tracks (optional)

## Good First Issues

Good first issues make the project welcoming to contributors. Without them, the project feels closed.

- [ ] At least 5 issues are labeled `good first issue`
- [ ] Each good-first-issue has:
  - [ ] Clear description of what needs to be done
  - [ ] Clear acceptance criteria
  - [ ] Link to the relevant file(s)
  - [ ] Estimated effort (small/medium)
  - [ ] No existing PR open for it
